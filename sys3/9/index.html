    Chapter 9 File System Implementation¶

    上一章从用户视角介绍了 file、directory、path、mount 和 protection。本章进一步讨论文件系统如何实现这些接口：如何把路径名变成 inode，如何把 logical block 变成 physical block，如何管理空闲空间，如何缓存和恢复一致性。

    本章主线

    • File system 通常分层实现，每层只处理一类抽象转换
    • On-disk structures 保存持久 metadata，in-memory structures 提高运行时性能
    • FCB / inode 保存文件 metadata 和 data block pointers
    • open() 把路径查找结果转换成 open-file table 中的运行时对象
    • VFS 用统一接口支持多种 file systems
    • Directory 本质上保存 file name 到 inode / FCB 的映射
    • Disk block allocation 包括 contiguous、linked、FAT、indexed 和 combined scheme
    • Free-space management 可用 bitmap、linked list、grouping、counting 等方式
    • Cache、async write、read-ahead、logging 等机制影响性能和恢复能力

    1 File System History¶

    文件系统随着硬件、OS 和应用需求演化。

    File System 演化
    阶段 时间 特点
    Early File Systems 1950s-1970s 基础、定制化，常为特定 OS 或特定计算机模型设计
    Hierarchical File Systems 1970s-1980s 引入 directories，典型如 UNIX file system 和 Microsoft FAT
    Network File Systems 1980s-1990s 支持网络访问，典型如 NFS
    Journaling File Systems 1990s-2000s ext3、ext4、NTFS 等先记录变更，再执行操作，便于 crash recovery
    Modern File Systems 2000s-Present ZFS、Btrfs 提供 snapshots、dynamic volume management、data integrity checks；GFS、S3 等面向大规模分布式存储

    文件系统演化的共同方向

    文件系统不只是“存文件”，还要解决层次命名、并发、崩溃恢复、性能、完整性校验、网络访问和大规模扩展。

    2 File-System Structure¶

    File 是一组相关信息的 logical storage unit。File system 位于 secondary storage 上，对上提供 user/program interface，对下调用 disk driver 读写 blocks。

    常见 File Systems
    • Linux：ext2、ext3、ext4、ReiserFS、Btrfs 等
    • Windows：FAT、FAT32、NTFS
    • 其它：ZFS、GoogleFS、Oracle ASM、FUSE
    • CD-ROM 标准：ISO 9660

    File System 的核心转换

    File system 把用户看到的：

    path + offset + length

    转换成底层设备上的：

    physical disk blocks

    其中需要 file control block、directory、free-space map、cache、device driver 等多层协作。

    3 Layered File System¶

    文件系统通常分层实现，以降低复杂度和重复代码。

    3. 1 Logical File System¶

    Logical file system 负责文件系统的逻辑 metadata。

    Logical File System 的职责
    • 保存除 file content 外的 metadata
    • 保存 directory structure
    • 保存 file description，即 FCB（File Control Block）
      • name
      • ownership
      • permissions
      • reference count
      • timestamps
      • pointers to other FCBs
      • pointers to data blocks on disk
    • 输入：open/read/write filepath
    • 输出：read/write logical blocks

    3. 2 File-Organization Module¶

    File-organization module 理解 logical file blocks 和 physical file blocks 的对应关系。

    File-Organization Module

    • 把文件内部 logical block number 转换成 disk physical block number
    • 管理 free space
    • 输入：read logical block 3、write logical block 17
    • 输出：read physical block 43、write physical block 421

    3. 3 Basic File System¶

    Basic file system 在 Linux 中可对应 block I/O subsystem 一类功能。

    Basic File System 的职责
    • 分配并维护 buffers
    • buffers 可包含 file-system blocks、directory blocks、data blocks
    • buffers 同时作为 caches 提升性能
    • 输入：read physical block #43
    • 输出：向更底层提交同一 physical block 的读写请求

    3. 4 I/O Control¶

    最底层是 I/O control，包括 device drivers 和 interrupt handlers。

    I/O Control

    • 输入：read physical block #43、write physical block #124
    • 输出：写设备 controller memory / registers，触发真实磁盘读写
    • 还负责处理相关 interrupts

    3. 5 Layering Tradeoff¶

    Layering 的优点

    • 降低复杂度
    • 减少重复代码
    • 让不同 FS 复用通用 block I/O、cache、driver 层
    • 逻辑层可用不同实现方法替换

    Layering 的代价

    分层会增加额外函数调用、数据结构转换和间接层，可能降低性能。文件系统实现经常在清晰分层和性能优化之间折中。

    4 File System Data Structures¶

    文件系统需要持久保存 metadata，同时在内存中维护高速访问结构。

    4. 1 On-Disk Structures¶

    On-disk structure 含义 示例
    Boot control block 若 volume 存放 OS，第一块可保存启动信息 UFS boot block、NTFS partition boot sector
    Volume control block 保存 volume 的 block 数、block size、free-block count、free-FCB count 等 UFS superblock、NTFS master file table
    Directory 文件名到 ID / FCB pointer 的映射 directory entries
    Per-file FCB 每个文件的 metadata NTFS 中 FCB 可看作 relational database 的一行

    4. 2 In-Memory Structures¶

    In-memory structure 作用
    Mount table 每个 mounted volume 一个 entry
    Directory cache 加速 path translation
    Global open-file table 系统范围内已打开文件对象
    Per-process open-file table 每个进程自己的 file descriptors
    Buffers 保存正在传输或缓存的 disk blocks

    为什么需要内存结构

    On-disk structures 是持久事实，但每次操作都读磁盘会非常慢。内核把频繁访问的 metadata 和 data blocks 缓存在内存中，以减少磁盘 I/O。

    5 File Control Block and Inode¶

    FCB（File Control Block） 保存文件 metadata 和定位文件数据所需的信息。Unix 系统中常见实现是 inode（index node）。

    FCB / inode 常包含
    • 文件类型
    • owner / group
    • access mode / permissions
    • file size
    • timestamps
    • link count / reference count
    • data block pointers
    • indirect block pointers

    inode number 的范围

    Unix / UFS 中 inode number 通常只在同一个 file system 内唯一。跨 file system 时，需要结合设备号或 mount 信息才能唯一标识文件。

    6 File Creation and Open¶

    6. 1 File Creation¶

    创建新文件时，logical file system 要同时处理 FCB 和 directory。

    create() 的基本步骤

    1. Application process 请求创建新文件
    2. Logical file system 分配一个新的 FCB / inode
    3. 在目标 directory 中加入新 file name 与 FCB 的映射
    4. 初始化权限、owner、timestamps、size 等 metadata

    6. 2 open()¶

    open() 把路径名解析结果转换成运行时 file handle。

    open() 的基本流程
    1. 搜索 system-wide open-file table，判断文件是否已在使用
    2. 若已在使用：
      • 创建 per-process open-file table entry
      • 指向已有 system-wide open-file table entry
    3. 若未在使用：
      • 搜索 directory 找到 file name
      • 从磁盘加载 FCB 到内存
      • 放入 system-wide open-file table
    4. 在 per-process open-file table 中建立 entry
      • 指向 system-wide open-file table entry
      • 保存 current file position
      • 保存 access mode
    5. 增加 system-wide entry 中的 open count
    6. 返回指向 per-process open-file table entry 的 handle / file descriptor

    后续 read、write、seek、close 都基于这个 handle 执行。

    close() 时发生什么

    • 进程 close 文件后，移除对应 per-process open-file table entry
    • system-wide open count 减 1
    • 若所有进程都 close 该文件：
      • 把必要的 in-memory directory / metadata 信息写回磁盘
      • 从 system-wide open-file table 中移除该 entry

    7 Mounting File Systems¶

    启动时，boot loader 会定位并挂载 root partition。外部 file systems 需要挂载到设备和目录树上。

    Mounting 相关结构
    • Boot block
      • 一系列连续 blocks，包含 boot loader memory image
      • Boot loader 定位并挂载 root partition
      • Root partition 中包含 kernel
    • In-memory mount table
      • 记录 mount points
      • 记录 mounted FS types
      • 记录访问目标 FS 的路径 / 设备信息
    • Unix mount table
      • in-memory mount table 中包含指向该设备上 file system superblock 的 pointer

    8 Virtual File Systems¶

    OS 常同时支持多种 file systems。问题是：system call 如何统一处理 ext4、FAT、NFS、procfs 等不同实现？

    David Wheeler

    All problems in computer science can be solved by another level of indirection, except for the problem of too many layers of indirection.

    VFS（Virtual File System） 就是文件系统中的这一层 indirection。

    8. 1 VFS 的作用¶

    VFS

    • OS 定义一套通用 FS interface
    • 所有具体 file systems 实现这套 interface
    • System calls 基于通用 interface 实现
    • 同一 syscall API 可用于不同 FS 类型
    • VFS 把 generic FS operations 与 implementation details 分离
    • OS 根据对象所属 FS 类型分派到对应实现

    8. 2 Linux VFS Objects¶

    Linux 定义了四类核心 VFS objects。

    Object 含义
    superblock 描述 file system type、size、status 和其它 metadata
    inode 描述某个文件 metadata，如 location、access mode、owner
    dentry 把 name 与 inode 关联，表示 directory layout 中的名字项
    file 进程打开文件后的运行时对象，表示实际打开状态

    8. 3 VFS Operation Tables¶

    VFS 为对象定义 operation sets，每个具体 file system 或 driver 实现这些函数表。

    write 的分派路径

    课件给出的路径：

    write syscall -> vfs_write -> indirect call -> ext4_file_write_iter

    如果写的是 NFS file，间接调用会分派到 NFS 对应的 file operations，而不是 ext4 的实现。

    file->f_op 什么时候设置

    一般在 open() / lookup 过程中，内核根据 inode 所属 file system 和文件类型初始化 struct file，并把 file->f_op 指向对应实现的 operation table。后续 read / write / ioctl 等通过这些函数指针分派。

    9 Directory Implementation¶

    Directory 本质上是一种特殊文件，保存 file name -> inode 的映射。

    9. 1 Directory Entry¶

    目录项通常保存 inode number、entry length、name length 和 file name。

    课件示例字段
    • inode number：目标文件 inode 编号
    • rec_len：directory entry 长度，通常按 4 的倍数对齐
    • name_len：文件名长度
    • name：文件名内容

    rec_len 允许目录项被删除后留下可复用空间，便于后续插入新 entry。

    9. 2 Directory Search Structures¶

    实现 做法 优缺点
    Linear list directory 是 file names 与 metadata pointers 的线性列表 简单，但搜索慢
    Ordered list / B+ tree 按名字排序或使用树结构 查找更快，实现更复杂
    Hash table 用 file name hash 定位 bucket 查找快，但需处理 collisions

    Unix vs Windows

    • Unix 把 directories 当作包含特殊数据的 files
    • Windows 对 directory 和 file 区分更强，创建和操作 directory 需要专门 system calls

    9. 3 File Open / Read Revisited¶

    open() 搜索系统范围 open-file table；若没找到，就搜索 directory structure 找 file name，找到后把 FCB 复制到内存中的 system-wide open-file table。

    创建新文件时目录和 FCB 如何配合

    • 分配新的 FCB / inode
    • 在目录文件中加入 directory entry
    • directory entry 把 file name 映射到新 inode number
    • 初始化 inode metadata 和空 data block mapping

    10 Disk Block Allocation¶

    文件需要分配 disk blocks 保存数据。不同 allocation methods 在连续性、随机访问、文件增长、碎片和可靠性之间取舍。

    10. 1 Contiguous Allocation¶

    Contiguous allocation 为每个文件分配一段连续 disk blocks。Directory 只需保存起始 block 和长度。

    Contiguous Allocation 的优点

    • 顺序访问几乎不需要磁头来回移动
    • random access 简单：start + offset
    • metadata 小，只需 start block 和 length

    Contiguous Allocation 的问题

    • 难以找到足够大的连续 free space
    • 有 external fragmentation
    • 可能需要 compaction / defrag，代价高
    • 文件增长困难
      • 复制到更大的 hole：开销高
      • 让用户预估最大文件大小：不方便且可能产生 internal fragmentation
      • 把文件拆成多个 contiguous chunks：形成 extent

    10. 2 Linked Allocation¶

    Linked allocation 把文件组织成 disk blocks 的 linked list。每个 block 包含指向下一个 block 的 pointer，文件以 nil pointer 结束。

    Linked Allocation 的优点

    • Blocks 可以散落在磁盘任意位置
    • 没有 external fragmentation
    • 不需要 compaction
    • 文件增长较容易

    Linked Allocation 的问题

    • 定位第 i 个 block 可能需要顺链走很多步
    • Random access 很差
    • 每个 block 要存 pointer，浪费空间
      • 课件例子：512 bytes block 中 4 bytes pointer，浪费约 0.78%
    • Pointer 损坏会破坏后续链表，可靠性差
    Cluster 改进

    可以把多个 blocks 组成 cluster，减少 pointer 数量、提高吞吐；但 cluster 可能造成 internal fragmentation。

    10. 3 File-Allocation Table¶

    FAT（File Allocation Table） 是 linked allocation 的变体。每个 block 的 next pointer 不放在 block 内部，而放在一张集中表中。

    FAT 的意义

    FAT 把链表指针集中起来，减少数据 block 内部指针污染，也方便缓存整张或部分 allocation table。但 FAT 本身可能很大，且仍保留 linked allocation 的链式访问特征。

    10. 4 Indexed Allocation¶

    Indexed allocation 为每个文件维护 index blocks，index block 中保存指向文件 data blocks 的 pointers。

    Indexed Allocation 的优点

    • 支持 random / direct access
    • 没有 external fragmentation
    • 支持 sparse file 中的 holes

    Indexed Allocation 的代价

    • index block 本身占空间
    • 小文件可能浪费 index block
    • 大文件需要多级 index 或 linked index blocks
    Index Blocks 如何扩展
    • Linked index blocks：多个 index blocks 链接起来支持大文件
    • Multiple-level index blocks：多级索引，例如二级索引
    • Combined scheme：小文件用 direct pointers，大文件逐步使用 indirect pointers

    10. 5 UNIX Inode Combined Scheme¶

    UNIX inode 是 combined indexed allocation 的典型例子。

    UNIX FCB / inode 指针

    课件给出 inode 中前 15 个 pointers：

    • 前 12 个：direct blocks
    • 后 3 个：indirect blocks
      • single indirect
      • double indirect
      • triple indirect

    最大文件大小计算

    若：

    • block size = 512 bytes
    • pointer size = 4 bytes

    一个 indirect block 可存：

    \[ 512 / 4 = 128 \]

    个 block pointers。

    最大文件大小约为：

    \[ 12 \times 512 + 128 \times 512 + 128^2 \times 512 + 128^3 \times 512 \]

    若 block size 改为 4 KB，一个 indirect block 可存 4096 / 4 = 1024 个 pointers，最大文件大小会大幅增加。

    10. 6 Allocation Method Comparison¶

    Method Sequential Access Random Access Fragmentation 文件增长
    Contiguous 很好 很好 external fragmentation 困难
    Linked 可接受 很差 无 external fragmentation，可能有 cluster 内碎片 容易
    Indexed 较好 较好 无 external fragmentation，有 index overhead 较容易

    Disk I/O 非常慢

    课件用数量级说明：2011 年 Intel Core i7 Extreme Edition 990X 约 159,000 MIPS。

    • 普通磁盘约 250 IOPS：

      \[ 159000 / 250 \approx 630 \]

      即一次磁盘 I/O 时间内 CPU 可执行约 630 million 条指令。

    • 快速 SSD 约 60,000 IOPS：

      \[ 159000 / 60000 \approx 2.65 \]

      即一次 I/O 仍相当于数百万条指令时间。

    因此文件系统设计要尽量减少 disk I/Os。

    11 Free-Space Management¶

    文件系统需要维护 free-space list，跟踪哪些 blocks / clusters 可用。删除文件后，其占用空间必须被回收。

    11. 1 Bitmap Free-Space Management¶

    Bitmap / bit vector 为每个 block 使用一个 bit 标记空闲或已分配。

    Bitmap 的优点

    • 空间紧凑
    • 容易找到连续 free blocks
    • 适合配合硬件位操作或内存扫描优化

    Bitmap 大小

    课件示例：

    • block size = 4 KB = 2^12 bytes
    • disk size = 1 TB = 2^40 bytes

    block 数：

    \[ n = 2^{40} / 2^{12} = 2^{28} \]

    bitmap 需要 2^28 bits = 256 Mbits = 32 MB。

    若 cluster = 4 blocks，则只需 64 Mbits = 8 MB。

    11. 2 Linked Free Space¶

    Linked free space 把所有 free blocks 串成 linked list。

    优点 缺点
    不浪费额外专门空间，可使用 free block 内部保存 pointer 难以快速找到连续空间
    分配单个 block 简单 可能需要额外 I/O 遍历链表
    通常不需要遍历整个 list，只取第一个 free block 多块连续分配效率差

    11. 3 Grouping and Counting¶

    简单 free-block linked list 效率不高，因为分配多个 free blocks 可能需要多次遍历或额外 I/O。

    Grouping

    在第一个 free block 中保存 n-1 个 free block addresses，再保存指向下一个 index block 的 pointer。

    这样一次读 index block 就能得到多个 free blocks，不必每分配一个 block 都顺链访问一次。

    Counting

    使用 (starting block, count) 表示一段连续 free blocks。

    因为磁盘空间经常成片分配和释放，counting 能紧凑描述连续空闲区域，也更容易分配连续 blocks。

    12 File System Performance¶

    文件系统效率和性能取决于多方面设计。

    影响 FS Performance 的因素
    • Disk allocation algorithms
    • Directory algorithms
    • Directory entry 中保存哪些 metadata
    • Metadata structures 是预分配还是按需分配
    • Data structures 是 fixed-size 还是 varying-size

    12. 1 Improving Performance¶

    常见优化

    • 把 data 和 metadata 放近，提高 spatial locality
    • 使用 cache，把频繁访问 blocks 留在内存
    • 使用 asynchronous writes
      • 可被 buffered / cached，因此返回更快
    • 对必须同步落盘的数据使用 synchronous writes
      • app 可主动要求，OS metadata 有时也必须这样做
    • Free-behind
      • 顺序访问时，移除已经读过且不再需要的 previous page
    • Read-ahead
      • 预测顺序访问，提前读入后续 pages
    Reads frequently slower than write: really?

    从应用视角看，write 可能很快返回，因为它只是写入 page cache / buffer cache，稍后异步落盘；而 read 若 cache miss，就必须等待磁盘把数据读回来。因此很多情况下 read 看起来比 write 慢。

    但若要求 synchronous write，write 必须等数据真正到达稳定存储，可能比普通 read 更慢。

    12. 2 Page Cache and Unified Buffer Cache¶

    OS 中有不同层次的 cache：

    • Page cache：缓存 memory-mapped I/O 的 pages，例如 memory-mapped files
    • Buffer / disk cache：文件系统用于 disk I/O 的 block cache

    早期系统中，memory-mapped file 和普通 file I/O 可能被缓存两次，造成 double caching。

    Unified Buffer Cache

    Unified buffer cache 使用同一套 page cache 同时缓存 memory-mapped pages 和普通 disk I/O，避免同一文件数据在系统中出现两份缓存。

    13 Recovery¶

    文件系统必须在 crash 后尽量恢复一致状态。

    13. 1 Consistency Checking¶

    Consistency checking 会比较 directory data 和磁盘 metadata，检查是否一致。

    Consistency Checking 的局限

    • 全盘检查可能很慢
    • 某些损坏不一定能自动修复
    • 系统越大，crash recovery 时间越难接受

    13. 2 Backup and Log-Structured File Systems¶

    常见 recovery 方法包括 backup 和 logging。

    Log-Structured File System（LSFS） 把 metadata updates 顺序写入 circular log。

    Log Structured File Systems
    • 更新先顺序写入 log
    • 一旦 changes 写入 log，就认为 transaction committed，system call 可返回
    • 后台再把 log entries replay 到真实 file system 位置
    • transaction replay 后，可从 log 中移除
    • log 是 circular 的，但未 replay entries 不会被覆盖
    • garbage collection 可回收 / compact log entries
    • crash 后只需 replay log 中仍存在的 transactions

    Logging 的价值

    Logging 把随机 metadata 更新转成顺序写，并让 crash recovery 只需处理 log 中未完成的事务，而不是扫描整个文件系统。
