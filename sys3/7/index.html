    Chapter 7 I/O Systems¶

    I/O 系统是 OS 设计中的核心部分。CPU 和内存只负责计算与临时存储，计算机要和用户、网络、磁盘、显示设备等外部世界交互，必须依赖 I/O devices 和 OS 的 I/O subsystem。

    本章主线

    • I/O devices 种类极多，OS 需要用 device driver 屏蔽硬件差异
    • CPU 可通过 I/O instructions 或 memory-mapped I/O 访问设备寄存器
    • Polling 简单但会 busy-wait；interrupt 避免忙等但有上下文切换开销
    • DMA 让设备直接和内存传输大块数据，减少 CPU 搬运成本
    • Application I/O interface 把设备抽象成 block、character、socket、timer 等类别
    • Kernel I/O subsystem 负责 scheduling、buffering、caching、spooling、reservation、protection 和 error handling
    • I/O 性能常受 context switch、interrupt、copy、buffering 和 bus 带宽影响

    1 Overview¶

    I/O management 是 OS design and operation 的重要组成部分。

    为什么 I/O 管理复杂
    • I/O device 是计算机与用户和其它系统交互的主要方式
    • 设备种类非常多，例如 storage、communication、human-interface devices
    • 不同设备控制方式差异很大
    • 不同设备性能差异巨大
    • 新设备类型会不断出现
    • Device driver 必须封装设备细节，并向 OS 提供统一接口

    统一抽象的意义

    应用不应该知道每一种键盘、网卡、磁盘控制器或串口芯片的细节。OS 通过 device driver 和 I/O subsystem 把具体硬件行为转换成相对稳定的系统调用和内核接口。

    2 I/O Hardware¶

    I/O 硬件形式很多，但从 OS 视角看，常见概念包括 bus、port、controller 和 device registers。

    概念 含义
    Bus 连接 CPU、memory、controllers 等组件的互连结构
    Port 设备与系统连接的接入点
    Controller 控制设备的硬件部件，可集成在设备中或作为独立电路板
    Device driver OS 中控制设备的软件模块

    Controller 通常包含自己的 processor、microcode、private memory 和 bus controller。OS 不直接操作设备内部所有细节，而是通过 controller 暴露的寄存器和协议发出命令。

    2. 1 Device Registers¶

    设备通常提供若干寄存器，用于传输数据、发出命令和读取状态。

    常见 Device Registers
    • data-in register：设备给 CPU / OS 的输入数据
    • data-out register：CPU / OS 写给设备的数据
    • status register：设备是否 busy、是否出错、命令是否完成
    • control / command register：OS 写入命令，控制设备执行操作

    这些寄存器可能只有 1 ~ 4 bytes，也可能是 FIFO buffer。Device driver 会把 command、data 或指向 command/data 的 pointer 写入寄存器。

    2. 2 Direct I/O and Memory-Mapped I/O¶

    有些 CPU 架构提供专门 I/O instructions，例如 x86 的 in、out、ins、outs。

    方式 做法 适用场景
    Direct I/O instructions 使用专门 I/O 指令访问 I/O ports 多用于小寄存器访问
    Memory-mapped I/O 把设备寄存器或设备内存映射到 physical address space 适合大块设备内存，如显存

    Memory-Mapped I/O 也必须受保护

    若用户进程能直接写设备寄存器或 MMIO 区域，就可能绕过 OS 破坏设备状态、读取敏感输入或攻击系统。因此 I/O ports 和 MMIO pages 都必须由权限机制保护。

    3 Polling¶

    Polling 是最直接的 I/O 控制方式：CPU / driver 主动反复读取 status register，直到设备可用或命令完成。

    Polling 的基本流程

    对每次 I/O operation：

    1. 读取 status register，若设备 busy 则 busy-wait
    2. 设备空闲后，把 command 写入 command register
    3. 不断读取 status register，等待命令执行完成
    4. 读取执行状态，必要时 reset device status

    Polling 的问题

    Polling 会浪费 CPU，因为 CPU 在等待设备期间不能做别的工作。若设备很快，polling 的开销可接受；若设备很慢，busy-wait 会非常低效。

    4 Interrupts¶

    Interrupt 让设备在操作完成时主动通知 CPU，从而避免 CPU 长时间 busy-wait。

    Interrupt-Based I/O 的基本流程

    1. Device driver 向 controller 发出命令
    2. Driver 返回，OS 调度其它任务执行
    3. 设备完成命令后向 processor 发送 interrupt
    4. CPU 进入 interrupt handler
    5. OS / driver 读取结果并唤醒等待进程

    Interrupt 避免了忙等，但它不是免费的。一次 interrupt 需要保存现场、切换到内核处理、执行 handler，再恢复被打断的上下文。

    Interrupt Storm

    如果 interrupt frequency 极高，上下文切换和 handler 开销本身会消耗大量 CPU。此时系统可能改用 polling 或混合策略。

    Linux 网络栈中的 NAPI 就会在高网络负载下启用 polling，减少过高频率 interrupt 带来的 CPU 浪费。

    4. 1 Interrupt Vector Table¶

    CPU 需要根据 interrupt / exception 类型找到对应处理入口，这通常通过 interrupt vector table 完成。

    不同架构示例
    • Intel Pentium：通过 interrupt vector table 查找不同中断处理入口
    • ARM64 Linux
      • 定义 vector table
      • 把 vector table 地址写入 VBAR（Vector Base Address Register）
    • RISC-V64 Linux
      • 定义 exception table
      • 把 handle_exception 写入 stvec（Supervisor Trap Vector Base Address Register）
      • handle_exception 再跳到具体 exception table entry

    4. 2 Interrupts and Exceptions¶

    Interrupt 也常被用来处理 exceptions。

    常见 Exception
    • protection error：访问违反保护规则
    • page fault：内存访问找不到合法映射或权限不满足
    • software interrupt：用于 system calls

    在多 CPU 系统中，不同 CPU 可以并发处理中断；有时会专门指定某个 CPU 处理某类 interrupt。

    4. 3 SMP IRQ Affinity¶

    Linux 从 2.4 kernel 开始支持把特定 IRQ 分配到指定 processors 或 processor groups，这称为 SMP IRQ affinity。

    IRQ Affinity 的作用

    • 控制硬件事件由哪些 CPU 处理
    • 在多网卡服务器中，把不同 NIC 的 interrupt 绑到不同 CPU
    • 对同时有重磁盘和重网络负载的数据库服务器，可让某些 CPU 更偏向 disk controller，另一些 CPU 更偏向 NIC
    • 提升 cache locality 和负载均衡能力

    5 Direct Memory Access¶

    DMA（Direct Memory Access）让 I/O device 和 memory 直接传输数据，CPU 不再逐字节搬运。

    DMA 的基本思想

    • OS 向 DMA controller 发出命令
    • 命令包含 operation、memory address、byte count 等信息
    • 设备 / DMA controller 直接在设备和内存之间传输大块数据
    • 传输完成后，设备 interrupt CPU

    DMA 需要设备或系统中有 DMA controller。真实系统中，driver 常把 command descriptor 的 pointer 写入设备 command register，而不是把所有数据逐字节写入寄存器。

    为什么 DMA 能提升性能

    没有 DMA 时，CPU 需要通过 programmed I/O 反复读写设备寄存器，可能一次只搬运一个 byte 或 word。

    DMA 把大块数据传输交给硬件，CPU 只负责设置命令和处理完成 interrupt，因此能减少 CPU 占用和内存复制路径上的开销。

    6 Application I/O Interface¶

    Application I/O interface 把设备行为封装成若干通用类别，应用通过系统调用访问设备，而不是直接操作硬件。

    Device-driver layer 隐藏 I/O controller 的差异。每个 OS 都有自己的 I/O subsystem 和 driver framework。若新设备遵循已有协议，就可能复用已有 driver 或 framework。

    Linux 的设备接口

    Linux 中很多设备可像文件一样访问。例如 /dev/tty、/dev/sda 都是设备文件。

    对低层、设备专有操作，Linux 提供 ioctl 这类 escape hatch，让应用把特定命令传给 device driver。

    6. 1 Characteristics of I/O Devices¶

    I/O devices 可从多个维度分类。

    维度 例子
    数据组织 character-stream 或 block
    访问方式 sequential 或 random-access
    调用语义 synchronous、asynchronous，或两者都支持
    共享性 sharable 或 dedicated
    速度 慢速键盘到高速 SSD / NIC
    方向 read-write、read-only、write-only

    6. 2 Device Classes¶

    OS 通常把设备归入若干 broad classes。

    类别 典型操作 示例
    Block I/O read、write、seek disks、SSDs
    Character I/O / Stream 按字符或字节流读写 keyboard、mouse、serial port
    Memory-mapped file access 文件映射到 address space mmap()
    Network sockets 网络协议读写 TCP/UDP sockets、Unix sockets
    Clocks and timers 当前时间、elapsed time、timer system timer

    ioctl 的位置

    标准 read/write/seek 无法覆盖所有设备特有能力。ioctl 允许应用把专有命令传给 driver，但也会扩大接口复杂度和安全风险。

    6. 3 Block and Character Devices¶

    Block devices 以 block 为单位访问数据，例如 disk drives。

    Block Device
    • 支持 read、write、seek
    • 可通过 raw I/O、direct I/O 或 file-system access 使用
    • 支持 memory-mapped file access
    • 常配合 DMA 提高吞吐

    Character devices 包括 keyboards、mice、serial ports 等。它们差异非常大，通常更像顺序 byte stream。

    6. 4 Network Devices¶

    Network devices 与 block / character devices 差异很大，因此常有自己的接口。最常见的是 socket interface。

    Socket Interface

    Socket 把 network protocol 与具体网络设备操作分离。应用使用 socket API，不需要直接知道网卡寄存器或驱动细节。

    某些非网络通信也可用 socket 抽象实现，例如 Unix domain socket。

    6. 5 Clocks and Timers¶

    Clocks and timers 也可被视作 character devices。它们提供：

    • current time
    • elapsed time
    • timer event

    普通 timer resolution 可能约为 1/60 second，某些 OS 提供更高分辨率的 timer。

    7 Synchronous and Asynchronous I/O¶

    I/O 调用语义会直接影响进程是否等待。

    类型 行为 特点
    Blocking I/O 进程挂起直到 I/O 完成 简单，但可能低效
    Non-blocking I/O 调用立即返回当前可用数据或状态 需要应用自己检查 readiness
    Asynchronous I/O I/O 执行期间进程继续运行，完成后被通知 高效但更难使用

    select 的位置

    Non-blocking I/O 常配合 select / poll / epoll 使用。应用先检查某个 fd 是否 ready，再调用 read 或 write 真正传输数据。

    8 Kernel I/O Subsystem¶

    Kernel I/O subsystem 在应用和硬件之间提供共享机制、性能优化和保护。

    8. 1 I/O Scheduling¶

    OS 维护 per-device request queue，并对请求排序。

    I/O Scheduling 的目标

    • 公平性
    • 吞吐
    • latency
    • quality of service
    • 减少随机访问开销

    磁盘调度属于 I/O scheduling 的典型例子。

    8. 2 Buffering¶

    Buffering 是在设备间传输数据时临时把数据放入内存。

    Buffering 的用途
    • 处理设备速度不匹配
      • 例如从 network 接收数据，再写入 SSD
    • 处理设备传输粒度不匹配
      • 例如网络分片重组成完整 message
    • 维护 copy semantics
      • 例如 write() 返回后，应用缓冲区可被修改，OS 仍能完成后续写入
    • 使用 double buffering 让一个 buffer 被设备使用时，另一个 buffer 可被应用或内核处理

    8. 3 Caching¶

    Caching 保存一份数据副本以便快速再次访问，是 I/O 性能的关键。

    Buffering vs Caching

    • Buffering 主要解决传输过程中的临时存放和速率 / 粒度 mismatch
    • Caching 主要解决重复访问的性能
    • 实际系统中同一块内存 buffer 可能同时承担 buffering 和 caching 角色

    8. 4 Spooling and Device Reservation¶

    Spooling 是为一次只能服务一个请求的设备维护输出队列。典型例子是 printing：多个进程的打印任务先进入 spool，再由 printer 顺序处理。

    Device reservation 提供对某些设备的 exclusive access。OS 需要提供 allocation / de-allocation system calls，但也要注意 deadlock。

    8. 5 Error Handling¶

    I/O 错误可能来自设备不可用、瞬时写失败、连接断开、坏块等。

    OS 的错误处理策略
    • 尝试 retry read / write
    • 记录 error frequency
    • 对错误频繁的设备停止使用
    • 向应用返回 error number / error code
    • 把问题写入 system error logs

    8. 6 I/O Protection¶

    OS 必须保护 I/O devices。例如如果键盘不受保护，keylogger 可以窃取 keystrokes。

    I/O Protection 的基本规则

    • 所有 I/O instructions 应定义为 privileged
    • 用户进程必须通过 system calls 执行 I/O
    • Memory-mapped I/O pages 必须通过页表权限保护
    • I/O ports 也必须受 CPU privilege 和 OS 控制

    8. 7 Kernel Data Structures¶

    Kernel 需要保存大量 I/O 状态。

    常见 I/O 状态
    • open file tables
    • network connections
    • character device state
    • buffers
    • memory allocation metadata
    • dirty blocks

    某些 OS 使用 message passing 实现 I/O，例如 Windows。包含 I/O 信息的 message 从 user mode 进入 kernel，再经过 driver，最后返回给 process。

    9 Transforming I/O Requests to Hardware Operations¶

    系统资源访问最终必须映射到具体硬件操作。

    进程读取磁盘文件的大致路径

    1. 进程发起 file read
    2. OS 判断文件位于哪个 device
    3. 把文件名转换为 device representation
      • FAT / UNIX 中常涉及 major / minor number
    4. 文件系统把 logical file offset 转成 disk block
    5. Block layer / driver 发起物理读
    6. 磁盘把数据读入 kernel buffer
    7. OS 把数据提供给 requesting process
    8. system call 返回

    10 Performance¶

    I/O 是系统性能的重要瓶颈之一。即使 CPU 很快，也可能被 I/O 路径上的等待、复制和中断拖慢。

    I/O 性能开销来源
    • CPU 执行 device driver 和 kernel I/O code
    • interrupt 导致 context switches
    • data buffering
    • memory copying
    • network traffic 尤其容易造成压力

    远程登录是一个典型例子：本地机器上敲下的每个字符都要传到远程机器，远程处理后再把结果传回来。若每个字符都触发多次上下文切换和网络发送，开销会非常高。

    Improve Performance

    • 减少 context switches 数量
    • 减少 data copying
    • 使用 large transfers、smart controllers、polling 减少 interrupts
    • 使用 DMA
    • 使用更智能的硬件设备
    • 平衡 CPU、memory、bus 和 I/O 性能，提高整体 throughput
    • 将部分 user-mode daemons 移入 kernel threads，减少边界切换

    11 Linux tty and ioctl Example¶

    课件用 Linux tty device 展示 I/O 路径如何落到实际内核代码。

    11. 1 Device Initialization¶

    /dev/tty 的创建与 tty_init 相关。初始化时内核注册 tty 设备，并在 /dev 下创建对应设备文件。

    11. 2 Device Write¶

    对 /dev/tty 执行 write，系统调用会进入 VFS 通用路径，最后调用 tty driver 的具体写函数。

    write 调用路径

    课件给出的路径可概括为：

    write syscall -> vfs_write -> tty_write

    这体现了 VFS / driver framework 的分层：系统调用入口通用，具体设备行为由 file operations 中的函数指针分发。

    11. 3 ioctl¶

    ioctl 用于把设备特有命令传给 driver。

    ioctl 的安全问题

    课件给出的路径为：

    ioctl syscall -> vfs_ioctl -> indirect call -> tty_ioctl

    ioctl 接口往往命令多、参数复杂、类型检查困难，且经常通过间接调用进入具体 driver，因此容易成为安全漏洞来源。

    12 Summary¶

    本章总结

    • I/O 设备种类繁多，OS 通过 device driver 提供统一访问接口
    • Device registers 包括 data、status、control / command 等
    • Polling 简单但 busy-wait；interrupt 避免忙等但有上下文切换开销
    • 高 interrupt 频率下，polling 或 NAPI 这类混合机制可能更高效
    • DMA 让设备直接与内存传输大块数据，减少 CPU 搬运
    • I/O 设备可按 block、character、network、timer 等类别抽象
    • Synchronous / non-blocking / asynchronous I/O 对进程等待行为不同
    • Kernel I/O subsystem 负责 scheduling、buffering、caching、spooling、reservation、error handling 和 protection
    • I/O 性能优化常围绕减少 context switch、copy、interrupt 和小粒度传输展开
