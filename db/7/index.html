    1 Functional Dependencies¶

    1. 1 Functional Dependency 的定义¶

    函数依赖（Functional Dependency, FD）是加在关系模式上的约束，用来描述：

    • 一组属性的取值
    • 能否唯一确定
    • 另一组属性的取值

    记作：

    \[ \alpha \to \beta \]

    其含义是：在关系模式 \(R\) 的任意合法实例中，只要两个元组在 \(\alpha\) 上取值相同，它们在 \(\beta\) 上也必须相同。

    \[ t_1[\alpha] = t_2[\alpha] \Rightarrow t_1[\beta] = t_2[\beta] \]

    理解方式

    • FD 是对所有合法关系实例都必须成立的约束
    • 它不是“某张具体表目前碰巧成立”的现象
    • 它是“业务语义决定的确定关系”
    示例：inst_dept(ID, name, salary, dept_name, building, budget)

    我们通常期望：

    • dept_name → building, budget
    • ID → name, salary, dept_name, building, budget

    但不会期望：

    • dept_name → salary

    1. 2 用 FD 定义键¶

    函数依赖是“键”概念的推广。

    • Superkey（超键）：若 K → R，则 K 是关系模式 R 的超键
    • Candidate Key（候选键）：若 K → R，且任意真子集 α ⊂ K 都不满足 α → R，则 K 是候选键

    也就是说：

    • 超键要求“能唯一确定整行”
    • 候选键还要求“最小”

    1. 3 Trivial / Non-trivial FD¶

    平凡函数依赖

    若 β ⊆ α，则 α → β 一定成立，称为平凡函数依赖（trivial FD）。

    例如：

    • ID, name → ID
    • name → name

    因此在判断范式时，我们重点关注的是非平凡 FD。

    1. 4 非平凡 FD 的分类视角¶

    课件特别强调：对非平凡 FD α → β，判断好坏时要看两件事：

    1. α 是否是超键
    2. β 中是否包含候选键中的属性（prime attribute）

    这正好对应：

    • BCNF：要求非平凡 FD 的左边必须是超键
    • 3NF：允许一部分左边不是超键的 FD 存在，但右边必须是主属性

    1. 5 Functional Dependencies 的用途¶

    我们使用 FD 来：

    • 指定合法关系必须满足的约束
    • 测试某个关系实例是否合法
    • 判断关系模式是否处于“好形式”
    • 在需要时进行分解（decompose）
    • 在少数场景下进行合并（combine）

    注意

    某个具体关系实例可能“碰巧”满足一个 FD，但并不代表这个 FD 是该模式上的真实业务约束。

    例如：某张 instructor 表当前可能刚好满足 name → ID，但这通常不是合法设计中应成立的依赖。

    不只是分解，有时也要合并

    例如：

    • dept_building(dept_name, building)
    • dept_budget(dept_name, budget)

    若二者都由同一个决定因素 dept_name 控制，可以合并成：

    • department(dept_name, building, budget)

    且不会引入重复。

    2 First Normal Form¶

    2. 1 Atomic Domain¶

    如果一个属性域中的值被当作不可再分的原子单位（atomic）使用，则称该域是原子的。

    非原子域的典型例子包括：

    • 属性值是一个集合
    • 复合属性直接塞进一个字段
    • 编码后可以再拆出业务含义的值

    2. 2 First Normal Form 的定义¶

    1NF

    若关系模式中所有属性的域都是原子的，则该关系模式属于第一范式（First Normal Form, 1NF）。

    1NF 的意义是：

    • 让关系模型中的每个单元格只放一个原子值
    • 避免非原子值带来的存储复杂性和重复存储

    2. 3 Atomicity 是“如何使用”的属性¶

    原子性不完全取决于数据长什么样，而取决于系统如何解释和使用它。

    学号不是天然原子

    假设学号是字符串：

    • CS0012
    • EE1127

    如果应用程序会从前两个字符中解析出院系，那么这个学号域就不再是真正原子的。

    这样做的问题：

    • 把业务语义编码进字符串
    • 逻辑隐藏在应用程序中
    • 增加系统耦合和维护成本

    结论

    1NF 是关系模式最基本的要求，但远远不够。要进一步判断关系设计是否“好”，还必须引入更高范式。

    3 Normalization Goals¶

    规范化（Normalization）的目标是：

    1. 判断一个关系模式是否处于“好形式”
    2. 若不是，则把它分解为若干更好的关系模式
    3. 希望分解后同时满足：
      • 每个子关系都处于较高范式
      • lossless join（无损连接）
      • 尽量 dependency preserving（保持依赖）

    理论基础主要包括：

    • functional dependencies
    • multivalued dependencies

    4 BCNF¶

    4. 1 BCNF 的定义¶

    Boyce-Codd Normal Form

    关系模式 R 相对于 FD 集 F 属于 BCNF，当且仅当对 F+ 中任意形如 α → β 的函数依赖，只要它是非平凡的，就必须满足：

    • α 是 R 的超键

    也就是说，BCNF 的核心要求是：

    • 所有非平凡 FD 的左边都必须足够强，强到能唯一标识整行

    4. 2 BCNF 违反示例¶

    典型违反

    对关系：

    • inst_dept(ID, name, salary, dept_name, building, budget)

    若有：

    • dept_name → building, budget

    由于 dept_name 不是超键，因此该关系不在 BCNF 中。

    4. 3 BCNF 分解¶

    若存在非平凡 FD α → β 违反 BCNF，则可把关系 R 分解为：

    • R1 = α ∪ β
    • R2 = R - (β - α)

    对 inst_dept 的分解

    令：

    • α = dept_name
    • β = {building, budget}

    则可分解为：

    • department(dept_name, building, budget)
    • instructor(ID, name, salary, dept_name)

    这样就把“院系决定楼和预算”的依赖放到了单独的关系中。

    5 Lossless Join 与 Lossy Join¶

    5. 1 Lossless Join¶

    对分解 R → R1, R2，若对 R 的所有合法实例 r 都有：

    \[ r = \pi_{R_1}(r) \bowtie \pi_{R_2}(r) \]

    则称该分解是无损连接分解（lossless-join decomposition）。

    对于二元分解，一个常用充分条件是：

    • R1 ∩ R2 → R1
    • 或 R1 ∩ R2 → R2

    直观理解

    交集属性如果能唯一决定其中一个子关系，就不会在连接时拼出伪元组。

    5. 2 Lossy Join¶

    若分解后再自然连接，可能产生原关系中并不存在的元组，则是有损分解（lossy decomposition）。

    错误分解会产生伪元组

    图中把 employee(ID, name, street, city, salary) 错误地分成：

    • employee_1(ID, name)
    • employee_2(name, street, city, salary)

    由于 name 不是键，连接后会把同名的 Kim 错误交叉组合，产生虚假的结果。

    经验法则

    不是“分得越细越好”。如果原关系中所有非平凡 FD 的左边本来都是超键，就不应该再机械分解。

    6 Dependency Preservation¶

    6. 1 定义¶

    若一个分解只需要在各个子关系内部检查依赖，就能保证原来所有 FD 都成立，则该分解是保持依赖的（dependency preserving）。

    形式化地，设 Fi 是 F+ 在 Ri 上的投影，则若：

    \[ (F_1 \cup F_2 \cup \cdots \cup F_n)^+ = F^+ \]

    则分解保持依赖。

    6. 2 为什么重要¶

    工程意义

    若分解不保持依赖，那么插入/更新时，为了验证某个 FD 是否被违反，可能必须先把多个表做连接，代价很高。

    6. 3 BCNF 与依赖保持的取舍¶

    核心结论

    • BCNF 强于 3NF
    • 但并不总能同时做到 BCNF、无损连接、依赖保持

    这是引入 3NF 的根本原因。

    7 Third Normal Form¶

    7. 1 3NF 的定义¶

    Third Normal Form

    关系模式 R 相对于 F 属于 3NF，当且仅当对 F+ 中任意 α → β，至少满足以下之一：

    • α → β 是平凡的
    • α 是超键
    • β - α 中的每个属性都属于某个候选键

    第三条允许了一定程度的冗余，因此 3NF 是对 BCNF 的最小放松。

    7. 2 3NF 的动机¶

    若直接追求 BCNF 会丢失依赖保持性，而某些业务约束又必须高效检查，此时就采用 3NF。

    3NF 是一种折中

    设：

    • advisor(s_id, i_id, dept_name)

    业务约束是：

    • 一个学生在某个院系中至多有一个导师

    重要 FD：

    • s_id, i_id → dept_name
    • i_id → dept_name
    • s_id, dept_name → i_id

    若拆成：

    • advisor(s_id, i_id)
    • instructor(i_id, dept_name)

    虽减少了重复，但检查“同一院系至多一个导师”就必须连接两表。

    因此 3NF 允许保留适度冗余，以换取依赖保持。

    7. 3 3NF 中的冗余¶

    3NF 不是完美无冗余

    某些 3NF 关系仍可能存在：

    • 信息重复
    • null 值
    • 更新异常

    因此：

    • BCNF 更干净
    • 3NF 更务实

    7. 4 BCNF 与 3NF 对比¶

    项目 BCNF 3NF
    严格程度 更强 更弱
    冗余控制 更好 允许少量冗余
    无损分解 总能做到 总能做到
    依赖保持 可能做不到 总能做到

    设计目标

    理想目标是同时满足：

    • BCNF
    • Lossless Join
    • Dependency Preservation

    如果三者不能兼得，通常在：

    • 放弃部分依赖保持
    • 或接受 3NF 带来的少量冗余

    之间做权衡。

    8 BCNF 还不够¶

    有些关系虽然满足 BCNF，但仍然存在严重冗余。

    BCNF 仍会有插入异常

    设：

    • inst_info(ID, child_name, phone)

    一个教师可能有多个孩子，也可能有多个电话号码。

    该关系没有非平凡 FD，因此形式上属于 BCNF；但若增加一个新电话号码，就要把它与该教师的每个孩子组合出多条元组。

    更合理的做法是拆成：

    • inst_child(ID, child_name)
    • inst_phone(ID, phone_number)

    这说明仅靠 FD 和 BCNF 还不够，需要引入 MVD / 4NF。

    9 Functional Dependency Theory¶

    9. 1 Closure of F¶

    给定一组 FD F，由它逻辑推出的全部 FD 构成 F+，称为 F 的闭包。

    例如：

    • 若 A → B
    • 且 B → C

    则可推出：

    • A → C

    9. 2 Armstrong’s Axioms¶

    Armstrong 公理

    • Reflexivity（自反律）：若 β ⊆ α，则 α → β
    • Augmentation（增广律）：若 α → β，则 γα → γβ
    • Transitivity（传递律）：若 α → β 且 β → γ，则 α → γ

    这三条规则既：

    • sound：不会推出错误依赖
    • complete：能推出所有逻辑可推出的依赖

    9. 3 Additional Rules¶

    以下规则都可由 Armstrong 公理推出：

    • Union（合并）：若 α → β 且 α → γ，则 α → βγ
    • Decomposition（分解）：若 α → βγ，则 α → β 且 α → γ
    • Pseudotransitivity（伪传递）：若 α → β 且 γβ → δ，则 αγ → δ

    9. 4 Attribute Closure¶

    给定属性集 α，在 FD 集 F 下可由 α 推出的全部属性集合记为 α+。

    算法思想很简单：

    1. 初始令 result = α
    2. 只要存在 β → γ 且 β ⊆ result
    3. 就把 γ 加入 result
    4. 直到不再变化

    9. 5 Attribute Closure 的用途¶

    α+ 非常重要，常见用途有三类：

    1. 测试超键 若 α+ 包含 R 的全部属性，则 α 是超键
    2. 测试某个 FD 是否在 F+ 中 若 β ⊆ α+，则 α → β 成立
    3. 辅助找候选键

    9. 6 找 Candidate Key 的经验规则¶

    经验判断

    • 若某属性只出现在非平凡 FD 的左边，它通常应出现在某个候选键中
    • 若某属性只出现在非平凡 FD 的右边，它通常不应出现在候选键中
    • 若某属性完全不出现在任何非平凡 FD 中，它必须出现在候选键中
    例子
    • R=(A,B,C,D,E), F={AB→C, B→D, AD→E} 的候选键是 AB
    • R=(A,B,C,D,E), F={AC→BD, B→A} 的候选键是 ACE 和 BCE

    10 Canonical Cover¶

    10. 1 Canonical Cover 的含义¶

    一个 FD 集的规范覆盖（canonical cover），是与原 FD 集等价、但去掉了一切冗余依赖和冗余属性的“最简形式”。

    要求：

    • 与原 FD 集逻辑等价
    • 不含多余依赖
    • 不含多余属性
    • 每个左部唯一

    10. 2 Extraneous Attribute¶

    冗余属性

    对依赖 α → β：

    • 若左边某属性 A ∈ α 去掉后仍能推出 β，则 A 在左边是多余的
    • 若右边某属性 A ∈ β 去掉后，原依赖仍可由其余依赖推出，则 A 在右边是多余的

    10. 3 规范覆盖的计算思路¶

    1. 用 union 把左部相同的依赖合并
    2. 不断检查左边和右边是否有多余属性
    3. 删除冗余部分
    4. 重复直到不再变化
    示例

    对：

    • F = {A → BC, B → C, A → B, AB → C}

    可化简为：

    • A → B
    • B → C

    注意

    规范覆盖不一定唯一，不同化简路径可能得到不同但等价的结果。

    11 Testing and Decomposition Algorithms¶

    11. 1 检测依赖保持¶

    若要检验分解是否保持某个 FD α → β，可使用一个多关系闭包过程：

    1. result := α
    2. 对每个子关系 Ri，取 (result ∩ Ri)+ ∩ Ri
    3. 把所得属性并回 result
    4. 重复直到不再变化
    5. 若最终 result 包含 β，则该 FD 被保持

    这个方法是多项式时间，比直接算完整闭包更实用。

    11. 2 检测 BCNF¶

    判断某个非平凡 FD α → β 是否违反 BCNF，只需：

    1. 计算 α+
    2. 看 α+ 是否覆盖关系的全部属性

    若不能覆盖全部属性，则 α 不是超键，该 FD 违反 BCNF。

    检查子关系时不能只盯着原始 F

    原关系分解后，某个子关系中可能会出现原始 F 里没直接写出来、但属于 F+ 的新依赖。

    例如：

    • R=(A,B,C,D,E), F={A→B, BC→D}

    分出 R2=(A,C,D,E) 后，AC→D 属于 F+，可能继续导致 R2 违反 BCNF。

    11. 3 BCNF Decomposition Algorithm¶

    算法思想：

    1. 从 R 开始
    2. 若某个子关系 Ri 不满足 BCNF
    3. 取一个违反 BCNF 的非平凡依赖 α → β
    4. 用：
    5. Ri - β
    6. α ∪ β 替换 Ri
    7. 直到所有子关系都在 BCNF 中

    性质

    该算法保证：

    • 每个结果关系都在 BCNF 中
    • 分解是 lossless-join

    但不保证 dependency preserving。

    11. 4 3NF Decomposition Algorithm¶

    3NF 分解以规范覆盖 Fc 为基础：

    1. 对 Fc 中每个 FD α → β，创建一个关系模式 α ∪ β
    2. 若这些关系中没有任何一个包含原关系的候选键，则再补一个“候选键关系”
    3. 删除那些完全包含于其他关系中的冗余关系

    性质

    该算法保证结果：

    • 每个子关系都在 3NF
    • lossless-join
    • dependency preserving
    3NF 分解示例

    设：

    • cust_banker_branch(customer_id, employee_id, branch_name, type)

    FD 为：

    • customer_id, employee_id → branch_name, type
    • employee_id → branch_name
    • customer_id, branch_name → employee_id

    先求规范覆盖，可化为：

    • customer_id, employee_id → type
    • employee_id → branch_name
    • customer_id, branch_name → employee_id

    最终得到 3NF 分解：

    • (customer_id, employee_id, type)
    • (customer_id, branch_name, employee_id)

    12 Multivalued Dependencies and 4NF¶

    12. 1 为什么需要 MVD¶

    有时一个实体对两组属性分别形成“独立的多值集合”，这不是 FD 能表达的，而是多值依赖（MVD）。

    例如：

    • 一个教师有多个孩子
    • 一个教师又有多个电话号码

    这两个集合彼此独立，于是会在组合表中产生笛卡尔积式重复。

    12. 2 MVD 的定义¶

    记作：

    \[ \alpha \twoheadrightarrow \beta \]

    表示在给定 α 后，β 的取值集合与剩余属性的取值集合是相互独立组合的。

    表格化理解

    若 α ⇉ β 成立，那么在同一个 α 取值下：

    • 已有 (β_1, \gamma_1)
    • 也有 (β_2, \gamma_2)

    就必须能补出：

    • (β_1, \gamma_2)
    • (β_2, \gamma_1)

    12. 3 MVD 的例子¶

    对：

    • inst_info(ID, child_name, phone_number)

    成立的依赖是：

    • ID ⇉ child_name
    • ID ⇉ phone_number

    其含义是：给定同一个 ID，孩子集合和电话号码集合相互独立。

    FD 是 MVD 的特例

    若 α → β 成立，则必有 α ⇉ β。

    12. 4 Fourth Normal Form¶

    4NF

    关系模式 R 相对于依赖集 D 属于 4NF，当且仅当对 D+ 中任意 α ⇉ β，至少满足：

    • α ⇉ β 是平凡的
    • 或 α 是超键

    因此：

    • 4NF 是针对 MVD 的 BCNF
    • 若一个关系在 4NF 中，则它一定也在 BCNF 中

    12. 5 4NF 分解¶

    若 α ⇉ β 非平凡且 α 不是超键，则像 BCNF 一样分解：

    • R1 = α ∪ β
    • R2 = R - (β - α)

    4NF 分解性质

    4NF 分解算法保证：

    • 结果关系都在 4NF
    • 分解是 lossless-join

    Restriction of MVD

    当把依赖集 D 限制到某个子关系 Ri 上时，得到的 Di 包括：

    • D+ 中所有只涉及 Ri 属性的 FD
    • 以及所有形如 α ⇉ (β ∩ Ri) 的 MVD，其中 α ⊆ Ri 且 α ⇉ β ∈ D+

    4NF 检查与 4NF 分解算法都依赖这种“投影到子关系”的思想。

    13 Further Normal Forms¶

    在 4NF 之上还有更高范式，例如：

    • PJNF / 5NF（Project-Join Normal Form）
    • Domain-Key Normal Form

    但这些更一般的约束：

    • 难以推理
    • 缺乏方便的完备推理规则
    • 实际数据库设计中较少直接使用

    14 Overall Database Design Process¶

    14. 1 规范化在设计流程中的位置¶

    一个关系模式 R 可能来自：

    • E-R 图转换得到的一组表
    • 一个包含所有属性的“universal relation”式粗糙设计
    • 某种经验性、临时性的设计

    规范化的作用就是：

    • 检验这些关系是否合理
    • 并在必要时将其拆成更好的小关系

    14. 2 ER Model 与 Normalization 的关系¶

    若 E-R 图设计得非常好，通常转换出的表已经基本不需要再规范化。

    但现实中仍可能出现：

    • 实体内部的非键属性决定其他非键属性
      例如：department_name → building
    • 关系集中的非键依赖

    这些都说明原 E-R 设计还不够好。

    14. 3 Denormalization for Performance¶

    有时为了性能，会故意采用反规范化（denormalization）设计。

    例如为了快速显示课程及其先修课信息，可以：

    • 建一个冗余表
    • 或建立物化视图

    优点：

    • 查询更快

    代价：

    • 占用更多空间
    • 更新更复杂
    • 维护成本更高
    • 容易写出额外同步逻辑错误

    14. 4 规范化抓不到的坏设计¶

    满足范式不代表设计就优秀

    例如：

    • 把 earnings_2004, earnings_2005, earnings_2006 分成多个表
    • 或直接做成交叉表列名

    它们可能形式上满足 BCNF，但：

    • 跨年份查询困难
    • 每年都要新增表或新增列
    • 结构缺乏扩展性

    14. 5 Temporal Data¶

    时间数据建模是规范化之外的另一类复杂问题。

    典型做法是给关系增加：

    • start
    • end

    来表示有效时间区间。

    时间维度带来的变化

    • 普通 FD 可能在整体关系上不再成立
      例如地址随时间变化，ID → street, city 不再全局成立
    • 但它可能在每个snapshot（时间切片）上成立
    • 还要额外保证同一对象的时间区间不能重叠
    • 外键引用也可能需要引用“历史版本”

    15 Practice Example¶

    综合练习

    设关系模式：

    • R = (A, B, C, D, E)

    函数依赖集合为：

    • F = {AB → C, B → D, AD → E}

    请完成：

    1. 找出所有候选键
    2. 判断 R 属于 BCNF、3NF，还是都不属于
    3. 若不在 BCNF 中，将其分解为 BCNF 关系，并判断该分解是否保持依赖

    这道题综合考察：

    • 属性闭包
    • 候选键判断
    • BCNF 违规检测
    • BCNF 分解
    • dependency preservation

    16 Supplement: 3NF Decomposition Algorithm 正确性要点¶

    课件最后给出了 3NF 分解算法的证明，复习时抓住结论即可。

    证明要点

    • 依赖保持：因为规范覆盖 Fc 中的每个 FD 都会对应至少一个生成出来的关系
    • 无损连接：算法确保分解后的某个关系中含有原模式的候选键
    • 每个子关系都满足 3NF：
      • 若某个非平凡 FD 的右边属性来自 β，则其左边必须是超键
      • 若右边属性来自 α，则它本身就是候选键中的属性，因此满足 3NF 的第三条件

    16. 1 为什么 3NF 的第三条件必不可少¶

    最后的关键理解

    在证明的第二种情况中，右边属性可能来自生成依赖的左边候选键，这时未必能证明新的决定因素是超键。

    这正说明：

    • 3NF 定义中“右边属性属于某个候选键”这一条不是多余的
    • 它恰好保证了 3NF 分解算法的正确性
